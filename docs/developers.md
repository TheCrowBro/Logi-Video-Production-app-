# For developers

Vdex is a static web app: plain HTML, CSS and JavaScript modules, no build step, no framework, no backend.

**Run it locally**
```sh
python3 -m http.server 8000   # then open http://localhost:8000
```
Camera, microphone, location, notifications and installing need https or `localhost`.

**Tests.** `npm install`, then `npx playwright install chromium` once and `npm test`: the browser specs in `tests/specs` run against a scratch copy of the app (the lock and vault, biometric unlock through a virtual authenticator, the call sheet builder and PDF, the update cycle, templates and themes, performance, money, weather and the service log). `npm run test:desktop` launches the desktop app (under `xvfb-run` on Linux). `.github/workflows/tests.yml` runs both on every push and pull request. GitHub's Ubuntu runner draws the app in DejaVu Sans, a wider font than many computers have for `system-ui` (Inter, San Francisco, Segoe UI), so a layout that only just fits on yours can scroll sideways there: to draw it as the runner does on Linux, run the specs with `FONTCONFIG_FILE` pointing at a fontconfig file that includes `/etc/fonts/fonts.conf` and rejects your own font (a `<selectfont><rejectfont>` block naming its family), and check that `fc-match sans-serif` then says DejaVu Sans. Specs 115 and 117 also check the menu and every page at the Large and Extra large text sizes.

**Signing the desktop apps (optional).** Add these repository secrets and the installers come out signed; without them they are unsigned, as before. Mac: `MAC_CERT_P12` (a Developer ID Application certificate exported as .p12 and base64-encoded), `MAC_CERT_PASSWORD`, and for notarization `APPLE_ID`, `APPLE_APP_PASSWORD` (an app-specific password) and `APPLE_TEAM_ID`; a signed and notarized Mac build updates itself through the same release metadata as Windows and Linux, and loses the “unidentified developer” warning. Windows is signed through Azure Artifact Signing: secrets `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` and variables `AZURE_SIGNING_ENDPOINT`, `AZURE_SIGNING_ACCOUNT`, `AZURE_SIGNING_PROFILE`, `AZURE_SIGNING_PUBLISHER` (the owner steps are in `docs/selling-desktop.md`). The Mac build uses the hardened runtime with the entitlements in `desktop/build/entitlements.mac.plist`.

**Where the website comes from.** The app lives at `https://vdex.crowmade.app`: a Cloudflare Worker that serves the static files, plus a small script (`cloudflare/worker.mjs`) that answers only `/buy` and `/licence/…` (owner steps and details in `docs/cloudflare.md` and `docs/selling-desktop.md`). `tools/stage-site.mjs` copies only the website (the pages listed in `tools/site-files.mjs`, `styles.css`, the manifest, `sw.js`, `js/`, `vendor/`, `icons/`, `.well-known/`), never the Android, desktop, docs, store or test sources, and refuses to publish if the offline list or a page names a file it leaves out. The *Publish the website* workflow (`.github/workflows/pages.yml`) works in two steps: a push to the working branch `claude/videographer-gear-app-xlg8eb` runs the browser test suite and, when it passes, the `mirror` job moves `main` to that commit and starts the workflow again on `main`, where the `cloudflare` job stamps the build and publishes it (without testing the same commit twice). So `main` is always exactly what is live, and a broken push never reaches anyone's phone. *Run workflow* on `main` publishes on demand. If the mirror step fails with "not a fast forward", someone committed to `main` directly: merge `main` into the working branch and push again. The old address (GitHub Pages) stopped when the repository went private. Every installed copy picks each update up by itself.

**Releasing updates.** Every push to the working branch deploys the web app once the tests pass (through `main`, as above): the Pages workflow first runs `tools/stamp-build.mjs`, which writes the commit into `js/version.js` and `sw.js` and regenerates the service worker's offline file list from the tree (and exits with 1, writing nothing, when a line it stamps cannot be found), so every deploy is one versioned set of files and every installed web copy picks it up on its next open (the page checks on start, when it comes to the front, when the network returns and hourly, then offers a reload). For the desktop apps, bump `VERSION` in `js/version.js` and commit, then run **Build desktop installers** with **Publish** ticked (or push a tag such as `v1.3.0`): the workflow builds the installers plus the `latest*.yml` update metadata and uploads them to `https://download.crowmade.app/vdex/` (the `vdex-downloads` R2 bucket; installers first, the `latest*.yml` files last), which installed Windows, Linux and signed Mac apps fetch by themselves through electron-updater (`desktop/updater.js`, generic provider); an unsigned Mac is told and sent to `download.html`.

**Making the installers.** `npm install` once, then `npm run dist -- --win`, `--mac` or `--linux` builds `Vdex-Setup-<version>.exe`, `Vdex-<version>.dmg` (and the `.zip` the Mac updater uses) or `Vdex-<version>.AppImage` into `dist/`, each on its own kind of computer (a Windows build on Linux also needs Wine). `.github/workflows/desktop.yml` builds all three on GitHub: open the **Actions** tab → **Build desktop installers** → **Run workflow**, then download them from the run's Artifacts (kept 3 days), or tick **Publish** to put them on the download address. The version comes from `js/version.js`.

**Desktop licences.** The desktop app has a 30-day trial, then needs a licence code (20 USD, up to 3 computers; free codes from the owner). `desktop/licence-codes.js` is the one implementation of the code format (Ed25519-signed, Crockford base32, Web Crypto only), shared by the desktop app, the Worker and the owner's generator. `desktop/licence.js` keeps the trial clock and the code in `licence.json` in the app's data folder, activates a code online once per computer (`/licence/activate` keeps a list per code in the `LICENCES` KV namespace: a random install ID, Mac/Windows/Linux and two dates) and rechecks weekly; a computer must reach the server once in 90 days, counted from the time on its signed receipt (the server's `at`, or the computer's own `clock` as it sent it and the server signed it back, where that is later and not later than the clock now), never from a time `licence.json` keeps, and a check counts as one that got through only with a receipt newer than the one kept. Each check also passes a `turn` the server replaces every time: an out-of-date one (a copy of the installation, or a lost answer) takes that install off the list with `409 stale`, and the app asks again under a new install ID, which it keeps only once the server has answered for it, so a copy needs a place of its own; until then that ID is noted for the code in `licence.json` (`next`), each check asks for it again (one the server listed though its answer was lost is answered `stale` once more, which takes it off, and is then asked for again) and **Remove the code** releases it too, so a lost answer leaves no place taken. Checks and activations run one at a time; while `licence.json` cannot be written nothing is asked (a turn that could not be kept would make the next check look like a copy's), and what could not be written is held for the rest of the run. An early user (`founder`) is one only while the copy in `desktop-state.json` says so too. A code entered while the server cannot be reached waits (`mode: 'pending'`): editing works for 14 days, once for each code on a computer (`waits` in `licence.json`, by the code's ref, kept after **Remove the code** and copied beside the trial's start in `desktop-state.json`, from which a wait missing in `licence.json` is taken back at every look; the days are counted by the latest time ever seen, and nothing about a wait is sent), and until the computer is on the code's list the code is no licence for cloud storage, backups or spreadsheets. A computer whose place was moved reports `released`. When a licence that was active on a computer stops covering it (`released`, `cancelled`, or `expired` past its end date), the state carries `lapsedAt`, the time this computer learned of it, by the latest time ever seen; it stays in every state, also after **Remove the code** and in the copy in `desktop-state.json`, until a code is activated there again, is never sent, and a code that was never active on the computer sets none. In `js/licence.js` a moved computer is `mode: 'released'` while `web()` is false (the website's own `released` is a phone or browser that is not on the licence). `js/licence.js` shows it in Settings → General → About & Licence and makes the store read-only through `store.setGate` when there is no working licence. The public keys live in `desktop/licence-keys.json`; while it is empty, licensing is off and every install that runs is marked as an early user (free for good). `tools/licence-generator.html` (built by `tools/build-generator.mjs` from its template) is the owner's offline page for keys and free codes, and signs requests to `/licence/admin` to look up, clear, cancel or restore a code; its last section posts an email address and the owner's `FORGET_SECRET` to `/licence/owner/forget`, which does for that address what **Delete my licence records** does for a sign-in (`forgetRecords()` in the Worker serves both; the address answers 404 until the secret, 20 characters or more, is set, and the secret is checked before the email address is read). Three more things in the Worker: Stripe's `charge.dispute.created` cancels a code and notes which dispute did (`x:<ref>` → `{ why: 'dispute', dispute }`), and `charge.dispute.closed` with `won` or `warning_closed` removes that cancellation and no other (a refund or the owner's cancel replaces the reason, and a dispute never replaces theirs); the store reviewers' sign-in (`REVIEW_EMAIL` and `REVIEW_CODE`, both or neither) makes one address sign in with a fixed 6-digit code, with no email sent and `/licence/web/start` answered as for any address, and counts wrong tries by the UTC day, for each requester (`CF-Connecting-IP`, an IPv6 address by its /64; stored as `rv:<day>:<tag>`, the tag a hash of the requester with the shop key and the day) and for everyone together (`rv:<day>`), in the isolate's memory before anything is awaited too, so a burst cannot outrun the counts: after `REVIEW_TRIES` (5) that requester is refused until the next day, and after `REVIEW_TRIES_ALL` (20) everyone is, the right code included and with a wrong code's answer (one in a million at 20 a day takes about 68 years on average to find; one stranger cannot use up the 20); secrets are compared with `same()` and `sameSecret()`, which look at every character. Specs 101–103 cover the format, the desktop rules, the Worker in workerd (needs `npm ci --prefix cloudflare`) and the page. **Prices with tax:** the licence is 20 USD plus the buyer's tax (Stripe adds it at checkout); `js/tax.js` holds the standard VAT and GST rates for the UK, the EU and Australia, whose law asks for the whole price up front. The Worker's `GET /licence/price` answers with the total for the request's country (`request.cf.country`), which the Buy buttons show on the website (`webLicence().localPrice`) and in the desktop app (`licence:price` through the bridge); never in the store apps. `download.html` lists every total, and spec 114 checks it against `js/tax.js`.

**The website's licence.** `js/licence-web.js` (the website, and the Play and iPhone apps, which open it) has a 30-day trial counted in the browser from the first time licences are on there, then a sign-in by emailed code (`/licence/web/…`). A sign-in token (`VDEX-WEB\0`) and a store app's place receipt (`VDEX-ACTIVE\0`) count only when signed with the shop's key on the page's `KEYS` line and naming the stored licence and install; `/licence/web/check` answers with a new token each time, and a check counts only with one newer than the token kept; the 90 days without a check run from the token's `iat`, or from the device's own `clock` signed into it where that is later and not later than the clock now, and a free licence's end date is judged from the token's `expires`. A browser without Ed25519 in Web Crypto checks the signatures with `vendor/ed25519.js` (@noble/ed25519), loaded only there. A store app given its place by a version before 1.4.0, which kept no receipt, is marked `oldSeat` at its first look and counts as on the list until its first place check. Licences are on unless `/licence/web/status` (asked at most every 6 hours, **Try again** included and whether or not an answer came: the time is kept before asking, and given back only when the request could not be sent at all, for want of a connection or because it was blocked; a plain GET with no cookie and no page address) answers with a note `{ kid, data, sig }` signed under the prefix `VDEX-STATUS\0` and saying `{ off: true, at }`: the page checks it with the public keys on its `KEYS` line (the same as `desktop/licence-keys.json`; spec 104 checks) and believes it for 3 days either side of `at`, by the latest time the browser has seen. No answer, any other answer, and an `on: false` stored by a version from before notes all mean on; a note kept from an earlier answer goes on counting while there is no answer, until its 3 days are up. A look at the licence (`state()`) waits for the answer 3 seconds at most, so a request held open cannot keep the licence unknown; an answer that comes later counts through `onChange`. The Worker signs a note with the shop's key while sign-in is not switched on (`WEB_SIGN_IN`); without `LICENCE_SHOP_KEY` it can sign none, so licences are then on. `store.loadLicence()` (from `js/app.js`) loads `js/licence.js`; while it cannot, or has not 30 seconds after it was asked for, the store's own gate keeps Vdex read-only and it tries again. A browser remembers a module that failed to load, for the rest of the visit and for every module that imports it, so `importChecked()` fetches `js/licence.js` (and `js/licence.js` so fetches `js/licence-web.js`) before importing it, and only an import that failed all the same makes later tries ask under `?try=n`. `js/licence.js` hands the state to `store.setPaid(paid, prompt, { links, backupUntil })`: cloud storage and spreadsheets need a working licence (`released`, a device the licence does not cover, is none, and neither is `pending`, a code or a store app's sign-in not yet added to the device online); `requireLicence(what)` waits until the licence is known (or could not be loaded) and never takes the last answer stored on the device (`vdex-paid`) on trust; `requireLicence('link')` also passes during the trial; `requireLicence('backup')` also passes for 30 days from `lapsedAt`, when this device learned that a licence covering it stopped covering it (the website keeps it as `lapsed`: set once, kept through signing out and in, and cleared only when a licence covers the device again; a store app moved off the list under an earlier version, which kept no day, gets it at its first look under this one). The tests run with licences off: `tests/run.mjs` makes an Ed25519 key for each run and puts its public half on the scratch copy's `KEYS` line (`testKey()` in `tests/lib.mjs`), and the test server answers the status address with a fresh note signed with it; specs get the private half as `VDEX_STATUS_KEY`, and `statusNote()` signs notes of their own.

**The Android app (Google Play)** is `android/`: a Trusted Web Activity generated with Bubblewrap (`@bubblewrap/core` 1.27) from `android/twa-manifest.json`, so the store app is a thin shell that opens the live site in Chrome with no browser UI, and website updates reach it on their own. It targets Android 16 (API 36), asks only for the notifications permission, and registers the web app's share target so files can be shared into it. Its package is `app.crowmade.vdex` (fixed for good by the first Play upload) and its icon opens `https://vdex.crowmade.app/index.html?src=play`. The `src=play` marker only comes with a start from the icon (a link, a share or a reload arrives without it), and `js/licence-web.js` records it on first sight (the Play app takes a place on the licence), together with an `android-app://app.crowmade.vdex` referrer. The share target takes real MIME types only (`text/plain`, `text/markdown`, `text/x-markdown` and Word's .docx type): Android refuses to install an app whose share filter lists file extensions, and its action must be the absolute `https://vdex.crowmade.app/share`. `.github/workflows/android.yml` builds the bundle and the apk on every change to `android/` (or by hand), signs them, and keeps them as the run's artifacts for 3 days; the run summary names the signing certificate. The app is no longer published as a public GitHub release, because it is sold on Google Play; the workflow's `unpublish` job removes the old `android-latest` pre-release. The upload key is `android/upload-key.keystore.enc` (AES-256, PBKDF2) and is unlocked with the `ANDROID_KEY_PASSPHRASE` repository secret, which is also the keystore password; without the secret the workflow signs with a throwaway key and says so. `.well-known/assetlinks.json` carries the upload key's certificate fingerprint; Google's own app-signing fingerprint has to be added there after the first Play upload. The file only counts at the root of the site's own domain, `https://vdex.crowmade.app/.well-known/assetlinks.json`. To change the shell (icon, name, start address, version), edit `twa-manifest.json`, raise `appVersionCode`, and regenerate with `npx @bubblewrap/cli@1.27.0 update --manifest=android/twa-manifest.json`, or edit `android/app/build.gradle` directly for the version alone. Store listing texts, the checklist for the account owner and the data safety answers are in `docs/google-play.md`; the store pictures are in `store/android/`, and `node tools/store-screenshots.mjs` remakes the screenshots from the app itself, with its sample data, as the installed Play app shows it.

**The iPhone app (App Store)** is `apple/`: a Capacitor 8 shell (`apple/capacitor.config.json`) that opens the live site in a web view limited to vdex.crowmade.app (an app-bound domain, so the service worker and the offline copy work inside it), with Capacitor's local-notifications, calendar (`@ebarooni/capacitor-calendar`), filesystem, share, haptics and app plugins, and two Swift plugins of its own in `apple/ios/App/App/`: `PurchasesPlugin` (StoreKit 2: the licence as a non-consumable in-app purchase, whose signed transaction goes to `/licence/apple/claim`) and `DocumentPickerPlugin` (the Files app for saving and opening, the print sheet, and files other apps hand to Vdex through the document types in `Info.plist`). `js/native.js` is the only module that touches `window.Capacitor`; everything else asks it and takes the web way when the answer is no, so browsers see no change. In the app the break alerts are scheduled with the phone (`js/notify.js`), the calendar adapter `apple` in `js/calendar.js` keeps a "Vdex bookings" calendar in step both ways, backups and shared files go through the Files app and the share sheet (`js/backup.js`, `js/share-in.js`), and the licence is bought through the App Store (`js/licence-web.js`; `/licence/apple/email` and `…/email/verify` let the buyer add an email address, at most three codes a purchase a day, and `/licence/apple/code` gives the desktop code on demand, never kept on the phone; a sandbox purchase gets a 30-day licence of its own with neither; `PurchasesPlugin` also listens to StoreKit's `Transaction.updates` from launch, so an Ask to Buy approval or an interrupted purchase reaches the page as a `transaction` event and is claimed). The receipt check (`cloudflare/apple-jws.mjs`) accepts only Apple's chain shape: the leaf, an intermediate carrying Apple's marker, the pinned root, with every signer a certificate authority. Cloud and calendar sign-ins run in the phone's own sign-in window (`WebAuthPlugin.swift`, `native.auth`): `js/providers.js` marks the app's sign-ins (a state ending in `~app`, or `?app=icloud` on the page's address for Apple), the website's pages come back to `js/return.js`, a plain script ahead of the app that hands a marked answer to the app on the `vdex://` address, and Google signs in on `signin-google.html` (`js/signin-google.js`) since Google's token client needs a page of ours. The Worker verifies Apple's signed transactions against the pinned Apple Root CA G3 (`cloudflare/apple-jws.mjs`) and takes App Store Server Notifications at `/licence/apple/notify`. Building and signing need a Mac with Xcode (`cd apple && npm install && npx cap sync ios && npx cap open ios`); [apple-app-store.md](apple-app-store.md) is the owner's step-by-step. Spec 113 drives the page with a stand-in for the plugins; spec 102 covers the Worker's purchase path with a certificate chain of its own.

**Start-up and storage costs.** Only the Bookings section and the shared modules load with the app (35 modules, about 570 KB unminified); the other eight sections, the tutorials, the menu's code and the search are fetched the first time they are opened, and `index.html` lists the start-up modules as `modulepreload` hints so a first visit fetches them in one go instead of discovering the import chain level by level. The service worker registers after the page has loaded and precaches with `cache: 'no-cache'`, so the offline copy costs revalidations rather than a second download. A build makes its cache whole as it takes over (it waits 20 seconds at most for the files) and again at each tidy (`refill()` in `sw.js`: the worker of the build before can delete a new build's cache while it installs). A tidy runs each time the worker starts and each time a page is opened, so one that could fetch nothing, for want of a connection, is made good at the next start that has one. Old caches are never dropped while a newer build is installing or waiting (`coming()`), neither at a tidy nor at the take-over. Store writes are coalesced: a burst of changes in one task is serialised and written once, and sealing flushes first. Spec 50 keeps all of this honest: the preload list must equal the real start-up graph, the lazy sections must not load at start-up, and a burst of writes must store once.

**The top bar and the menu.** The bar (`header.top` in `index.html`) is one row: the brand, `#topSearch` (the search control `#searchBtn`, between the brand and the buttons: a magnifier up to 560 px, a field-shaped button above that), `#lockBtn` (shown only while a PIN is set) and the hamburger `#menuBtn`. Everything else the bar once held is a row of the menu, a dialog (`#menu` inside its backdrop `#menuBack`) whose markup is also in `index.html`, so the rows keep their ids (`#helpBtn`, `#installBtn`, `#displayBtn`, `#cloudBtn` with `#cloudLabel`) and `js/app.js` and `js/install.js` wire, show and hide them as before; a row's own listener runs after the menu has closed. `js/menu.js` is fetched the first time the hamburger is tapped and only opens and closes the panel (focus, Tab and arrow keys, Escape, the backdrop, the version); like the search it opens only while the page itself can be used (`#app` not inert), so a menu whose file arrives after a form or the lock has opened stays shut. `paintCloud()` in `js/app.js` writes the sync state in three places on every store event: the word on the storage row, the sentence at the top of the menu (`#menuStatus`: a plain `div` while the state is `synced` or `off`, and otherwise a `button` that closes the menu and opens the storage sheet; the element is swapped, its id kept), and the hamburger's dot (`data-dot` = `amber` or `red`, absent when all is well) with the same words in its `aria-label`. `window.logiMenu` (`open({ show })`, `close()`, `isOpen()`) is how the rest reaches it without importing it: `sheet()`, `runTour()` and the lock screen close the menu before they open, so it is never left underneath one of them, and a tour step with `menu: true` shows it open but inert while the step points at something inside it. Spec 115 covers all of this.

**Search.** `js/search.js` is fetched the first time `#searchBtn` is tapped (or `/` or Ctrl+K is pressed while the page itself can be used; on Apple devices it is ⌘K, and Control+K is left to the system; the listener is in `js/app.js`). Once the top bar has scrolled out of sight, the Rolodex bar shows a magnifier of its own (`#navSearch`, made in `js/app.js`), which opens the same panel. `buildIndex()` reads `store.db` into a flat list of entries, one per thing that can be opened: a booking, and separately its quote, its invoice, its call sheet and its stripboard; a crew member, an item, a kit, a venue, a policy, a timecode log; the profile, each project template, the custom checklist lines, the price list and the billing texts. An entry has the page it is grouped under, a kind and an id, two display lines, and fields `[label, text, weight, { shown, at, tel }]`, each folded once (`fold()`: lower case, accents and marks dropped, a few letters such as ø and ß spelt out). A crew member also carries the group their role is filed under and the role's other names (`findRole()` in `js/roles.js`), as the Crew page's own search does. Records are read one at a time (`each()`), so one that cannot be read costs only itself. `find(query)` splits what was typed into words (punctuation around a word is dropped), keeps the entries in which every word is found in some field, and scores each as the sum, per word, of its best field: the field's weight (100 for a name or title down to about 12 for script text and linked names), raised when the word is the whole field, starts it or starts a word in it; ties go to the nearest date, then the name. A word of digits is also looked for in phone numbers with their punctuation removed. The index lives in memory only, carries the store's `revision()`, and is rebuilt when that has moved (on opening, and through `store.subscribe` while the panel is open); typing is debounced by 120 ms, and at most five results a page are drawn (sixty at a time once a chip is chosen), so thousands of records stay quick (spec 115 builds 7,000). A new collection or field becomes searchable by adding it to `bookingEntries`, `listEntries` or `ownEntries`. The panel (`#search` inside `#searchBack`, built on first use) is a dialog whose field is a combobox driving a list box (`#searchList`) of grouped options through `aria-activedescendant`; the chips are toggle buttons, counts are announced through `announce()` once typing pauses, and matches are marked with `<mark>` elements built from text nodes, never `innerHTML`. Choosing an option closes the panel and calls the `OPEN` table: `openBooking(id, patch)` for a booking and its documents, `openVenue`, `openLog(id, view)` in `js/pages/tcnotes.js`, `openSettingsSection`, and for the list pages (`showAll()` in `js/pages/crew.js` and `js/pages/gear.js` clears the page's own filter) the card with that `data-id` is scrolled to, outlined (`.found`) and focused; a field's `at` names the spot inside the record (a booking section's id, a note, a script line, a strip, the service log, a line of the price list or of a checklist). A project template lands on its card (`templateCard()` in `js/pages/settings.js`); a handler that could only open a Settings section answers with that section's name, which is then what is announced. The jump to a result keeps the Rolodex bar on screen (`window.logiShowNav(true)`). `openRecord(kind, id)` does the same for any other feature. `window.logiSearch` (`open({ show, query })`, `close(forget)`, `isOpen()`) is how the rest reaches it: `sheet()` and `runTour()` close it before they open, the lock screen closes it with `forget`, which also drops the index and what was typed, and a tour step with `search: true` shows the panel open but inert (calling `open({ show: true, query })` again changes the words it shows). Closing gives the focus back to whatever had it when the panel opened, or to `#searchBtn`; opened again with the same words, the list has the same chip, length and scroll position. On a touch screen Enter with nothing marked puts the keyboard away instead of marking the first result. Nothing is written to storage and no request is made. Spec 115 covers all of this.

**The calendar's two-way sync** (`runSync()` in `js/calendar.js`) never sets this device's clock against the calendar's. The map from a booking to its event keeps the hash of what Vdex last sent and `seen`, the calendar's own stamp of the event when Vdex last looked. A booking whose hash has changed since its push, or an event taken over without one, goes out as Vdex has it; otherwise an event whose stamp has moved (or is not known yet) is set against what was sent (`patchFromEvent()` compares with `eventOf()`, never with the booking's own boxes, so a finish Vdex made up for the calendar is not written back), and what differs is a calendar edit. A sync asked for while one runs runs when it ends (`link.again`), the map is saved only when it changed, and Disconnect keeps the calendar's id (`calendarFor` names the service it belongs to) so Connect uses that calendar again. Spec 107 drives it with a stand-in calendar.

**A page drawn again** (after every change, also one that arrives from a sync) goes through `redrawKeeping()` in `js/util.js`: the control that had the focus has it again, found by its kind, label, surrounding text and place among its like, and a box that was being typed in keeps its text and cursor. A restore (`replaceAll()`) stamps every record as changed now, so it outranks deletion marks made before it; `mergeDb()` also takes the ids of crew, items and kits that were deleted elsewhere out of the bookings and kits here. A call sheet marked sent keeps `sentHash`, a mark of everything it prints (`sentPrint()` in `js/callsheet.js`, built from stored facts only, so it is the same on every device), and reads "changed" when that no longer matches.

**Shared things** travel the way the crew link does: `pack()`ed into a URL fragment that no server ever sees. `crew.html#…` is the shoot (`kind: 'crew'`), `shared.html#…` a contact card (`contact`) or an equipment list (`gear`); each page has **Add to my Vdex**, a plain link to `index.html#add=<the same packed text>` (`addHref()`; opened by the Play app, whose referrer says so, it is `index.html?src=play#add=…`, so the app's mark goes along), and under it a line with **Copy link** for people whose Vdex is an app that no link opens (`elsewhere()`). `js/app.js` takes that fragment out of the address bar before anything else runs and parks it in `sessionStorage` (`vdex-add`, so it survives the lock, the terms, the PIN set-up and a sign-in round trip in that tab); `arrived()` in `js/share-add.js` waits until nothing stands in front of the app (`lock.isLocked()`, `store.isSealed()`, `tourSeen()`, `tourActive()`, a `.terms-gate` or `.lock` on the page), then shows a preview sheet, and only its Add button writes. With cloud storage linked, `ready()` first reads the cloud copy (`store.sync({ quiet: true, join: true })`, for at most four seconds: a device reads it only at start and when it comes to the front, so one left open would not hold what another device added from the same link, and would offer to add it again). A preview's button looks once more at the tap and draws the preview again, with a line saying so, when the booking, the person, the items or the kits it is about have arrived or gone meanwhile. When the last sync did not work (`cloud.status` is `needs-permission`, as with Google Drive about an hour after the last sign-in, or `error`), nothing could be read, and a preview that would add says so (`unread()`). Records a link makes get ids of their own on each device (`uid()`), never ids worked out from the link: with one id on two devices, the later copy, or a Delete or an Undo of it, would take the other device's work with it. So a device that could not read the cloud copy ends with a second copy after the sync, and nothing is replaced. One link is looked at at a time: a preview takes the place of the one before it, and of several links that wait only the newest is shown. `openAddFromLink()` is the same for a pasted or scanned link (the desktop app and the iPhone shell cannot be opened by a link). Everything read from a link goes through `readShared()` in `js/share-data.js` first: the link is at most 400,000 characters and 3 MB unpacked (`unpack(…, { max })` stops a deflate bomb early), only the listed fields of the three kinds survive, with their types checked and their lengths and list sizes capped (also in total: 2,500 strips and 1,000 cast names a shoot, 2,000 items and 5,000 kit places an equipment list; `cut` counts what was left out, and the pages and the preview say so), email addresses and websites are dropped unless they are plainly an address and an http(s) URL (a person on a shoot keeps other text as `emailText`, shown but never linked), and an unknown `kind` or a quote/invoice link is refused with a sentence. A higher `v` than this build knows is read as far as the allow-list goes and flagged (`newer`). Records made from a link carry `shared` (`{ ref, by, at }`; a booking also `updated`, `made`, `note`, `kitNote`, `contacts`, `producer`, `sent` and `rows`), which lives inside the record, so it syncs, merges and restores with it. A second import finds a booking, venue, item or kit by `shared.ref` and updates it. For a booking, `shared.sent` holds what the link last supplied for each single detail (title, client, dates, times, address, the call sheet's times and notes, the break; a venue the link made keeps its own), and an update overwrites a detail only while the booking still holds that value: one changed by hand is kept and named in the preview. The lines an imported booking carries (hires, schedule lines, shots, deliverables, strips; contacts by name in `shared.contacts`) are the link's when they carry `shared: true` or their id is in `shared.rows` (a form writes a line anew without the mark, and the stripboard keeps only a strip's own fields, so the ids are what lasts; `mergeBooking()` in `js/store.js` joins both copies' `shared.rows.strips`, so a sync never forgets a strip a link made): an update replaces those with the link's, keeps the rate, days and notes given to a person, a strip's notes, a shot's tick and a deliverable's link, and leaves lines made by hand where they are. An empty part of a link changes nothing, and a booking from before `shared.sent` existed takes every detail the link holds. A card updates a person without asking only when it is surely them (`matchContact()`: the same email address under the same name, or a record that came from a card with that name which the card does not contradict); a match by phone, by name or by email under another name is shown beside the card, with **Add as a new person** first, and one's own card (`ownCard()`) adds nobody. `billTo()` in `js/money.js` sends the quotes and invoices of a booking that came from a link to the person who shared it (`shared.producer`) and leaves out the contacts the link brought; changing the client by hand changes the name the document is headed to, nothing else. Suggested lines and the budget leave out the link's crew until one is given a rate, and suggested lines leave out the deliverables the link brought. `js/gear-import.js` is the one place equipment from outside is matched and merged: `roomForBooking()` and `roomForGear()` are asked before a link is applied, and an equipment link is followed by the same Undo as a file import (`offerUndo()`). `planGearImport(items, { existing, onSerial, onName, matchNames })` returns `{ rows: [{ item, match, why, action }] }` (`why` is `ref`, `serial` or `name`), the caller may change each row's `action` (`add`, `update`, `skip`; a row that is one's own item, `match.id === item.ref`, starts on `skip`), and `applyGearImport(plan, { kits, from })` applies it in one `update()`, leaving a kit that exists alone when every row it names was skipped; a spreadsheet import should feed it plain items under `GEAR_FIELDS`. Making a contact card or equipment link, or the Me page's **Contact card** code, works during the trial and with a licence (`store.requireLicence('link')`, `store.linksAllowed()`), and after the trial only with one; the crew link and opening any link never need a licence; adding respects read-only mode through `store.canChange()` and `update()`. Spec 116 covers all of it.

**Importing a kit list** (Equipment → Import…) is three modules, all loaded on first use, and no library. `js/table-read.js` turns a file or pasted text into rows of plain text cells: `readTableFile(file, { abandoned })` and `readTableText(text, { abandoned })` give `{ name, kind, sheets: [{ name, rows: [{ n, cells }], truncated, hidden }] }`, `n` being the row's number in the file; a row of an `.xlsx` also says which of its cells were number cells (`nums`: their columns), and those are read as the numbers they are, never by the guesses meant for typed text. Separated text is parsed by a small state machine (quoted cells with separators, line breaks and doubled quotes; a byte-order mark; `\r\n`, `\n` or `\r`; UTF-8, UTF-16 with a mark, otherwise Windows-1252), the separator is the one most of the first lines agree on (`sniffSeparator`: tab, semicolon, comma or bar, or none for a list of one item per line, which `listLines()` turns into Item / Quantity / Serial number columns, in time that grows with a line's length and no faster). An `.xlsx` is unzipped with `zipEntry()` from `js/docx.js` and read with a linear tag scanner (`tags()`, no pattern that has to guess where an element ends): the sheet names and paths from `xl/workbook.xml` and its rels, shared and inline strings, a formula's saved result (never evaluated), booleans, errors as empty cells, day numbers as dates when the cell's style has a date format (built-in ids, or a custom format with day or year letters), counted from 1904 when the workbook says so, and a number under a format of zeros alone padded the way it shows (000123); no other number format is applied. What a file is comes from its first bytes, not its name: an old `.xls`, a PDF, a Numbers or OpenDocument file and anything binary are turned down with a sentence. `LIMITS` caps a file at 20 MB, an unpacked zip entry at 60 MB and all the entries of one workbook at 80 MB together (the reader stops inflating there; `zipEntry()` takes the shared allowance as `budget`), 10,000 rows, 60 columns and 2,000 characters a cell; a worksheet is read once however often the workbook names it; and long loops give the page a turn every few milliseconds and end with an error coded `abandoned` once the caller's `abandoned()` says nobody is waiting (the sheet was closed, another list was chosen). `js/gear-columns.js` understands the rows: `layout()` finds the row of headings (or none), `guessColumns()` gives each column one of `TARGETS` from its heading (`HEADINGS`, ranked, plus looser word rules) and otherwise from what is in it (`profile()`: money, dates, small whole numbers, unique codes with digits, words that name kinds of kit), and `buildItems()` turns the rows into items under `GEAR_FIELDS` with per-row problems, passing over totals, repeated headings and group headings (which give the rows under them a category, and are returned by row and text in `passed`). An item has a `qty` only when its row gave one, so an update leaves an owned quantity alone. A row whose only cell is a word for a kind of kit in the name column (“Tripod”, “Lenses”) is an item unless it is written as a heading (capitals, a colon at the end) or the list opens with such a word, and never a heading while a Category column is mapped; `lone` in the result counts those rows, and the option `lone: 'headings' | 'items'` is the person's answer for all of them. Vdex's own register, known by its row of headings, keeps its categories as typed. `parseAmount`, `numberStyle`, `parseDate`, `dateOrder`, `parseQty`, `parseMonths` and `mapCategory` are exported and tested one by one; none of them tries a pattern on text longer than a value can be. `js/gear-import-ui.js` is the sheet: choose or paste, a card per column with a control to change it, the results under them, then `planGearImport(items, { matchNames: true })` and `applyGearImport()`; nothing from a file is ever set as HTML. `openGearImport({ file })` starts with a file already in hand: `js/share-in.js` offers it when another app hands Vdex a `.csv`, `.tsv` or `.xlsx`. `applyGearImport()` now also returns what `undoGearImport(done)` needs, which removes what an import added and restores what it updated wherever the record's `updatedAt` is still the import's and nothing uses it, with tombstones so a merge cannot bring the items back; an item's `lastService` (the asset register carries it) becomes a line in its service log. Before adding, `roomFor(change)` in `js/gear-import.js` tells whether the browser's storage has room: it makes the change on a copy of the database, measures the whole database as it would be saved (and, with a PIN, how much the encrypted copy would grow) and tries a test write of that size, so a list that would not fit is refused instead of being added and not saved (`roomForGear(plan, { kits, from })` is the same for an equipment plan; a shared booking can ask with its own change). Should a save be refused all the same, `js/store.js` says so in a toast and to screen readers, at most once a minute. The asset register writes a leading apostrophe before text that starts with `=`, `+`, `-` or `@` (so a spreadsheet does not run it) and the import takes it off again. A list of more than 200 items makes the Equipment page lay its cards out as they scroll into view (`.gear-many`, `content-visibility`). Spec 117 covers it, with sample files in `tests/fixtures/`.

Where the column headings come from, for the next person who adds some. Published by the tools themselves: EZOfficeInventory's data dictionary (Name, Asset #, Asset Identification Number, Group, Subgroup, Location Name, Product Model Number, Purchased On, Cost Price, Vendor, Description; ezo.io/ezofficeinventory/blog/data-dictionary), Cheqroom's import guide (Name, Category, Location, Kind, Brand, Model, Purchase Price, Purchase Date, Barcode, Kit Name; knowledge.cheqroom.com, "How to add and import items"), Sortly's bulk import article (Entry Name, Barcode/QR-1 Type; help.sortly.com) with the rest of its export columns as a migration guide lists them (Entry Type, Quantity, Min Level, Price, Value, Unit, Tags, Notes, Primary Folder, Subfolder-level1 to 4, Photo URLs, Barcode/QR1-Data, Sortly ID; itemtally.com/guides/switch-from-sortly), and Rentman's import articles (Code, Name, Type of Equipment, Rental/Sales, a "(Serial number)" suffix on serialised columns; support.rentman.io). No rental house or insurer was found that publishes the columns of its order export or equipment schedule, and MyGearVault, Asset Panda, Booqable and Current RMS do not list theirs publicly, so those two sample files are modelled on the usual layout (position, quantity, article, serial number, daily rate, replacement value, total; item, description, make, model, serial number, date purchased, replacement value) rather than on a named product, and the home-inventory template follows the columns the Excel, Numbers and Google Sheets templates share (item description, make/model, serial number/ID, date purchased, where purchased, purchase price, estimated current value). The two `.xlsx` samples were written by real writers, one with inline strings (openpyxl 3.1) and one with shared strings (LibreOffice Calc), and spec 117 builds a third by hand for the corners of the format.

**Getting paid** is built around links rather than a processor. `js/pay.js` turns the settings into Pay buttons with the balance and the invoice number filled in (PayPal.Me takes `name/amountCODE`, with the code left out when the currency is not one Vdex knows: `knownCode()` never guesses; Venmo and Cash App take the amount in the address, any payment page gets `{amount}` and `{reference}` substituted), plus bank lines and an EPC069-12 payload for the bank QR (euro amounts only, as the standard requires, and only for an account that is an IBAN: `isIban()` tests its shape and check digits). `snapshot(b, kind)` in `js/money.js` is the self-contained copy of a document that everything renders from; `shareLink` packs it with `js/link-pack.js` into `invoice.html#1.<base64url deflate-raw>` (`0.` when the browser has no CompressionStream), and `js/invoice-page.js` unpacks and draws it with the same `money-doc.js` renderer, so the client's page and the app can never disagree. The fragment never leaves the browser, which is why no server is involved. Payments live on the invoice as `payments[]`; `calc()` derives paid and balance from amounts rounded to cents once (each line, then the subtotal, the tax and the total, so every figure adds up to the next), and an invoice marked Paid with nothing recorded counts as paid in full, which keeps older records right. A suggested line carries where it came from (`src`: the shoot days, a crew member, the kit, the editing hours…; it never leaves the app), and `mergeSuggested()` brings the line it made up to date when the lines are asked for again, instead of adding a second one. A quote and an invoice each keep their own `updatedAt`, and a deleted one leaves `quoteGoneAt` or `invoiceGoneAt` on the booking: `mergeBooking()` in `js/store.js` keeps the newer of the two copies' documents, as it does for the budget and the stripboard. The ways to pay are a list (`billing.payMethods`, each `{ type, value, label }` or bank fields) drawn from `PAY_TYPES` in `js/pay.js`; `methodsOf()` also reads the older fixed fields, so earlier settings and earlier links still work. Spec 90 covers settings and the catalogue, buttons, QR, payments, the link, the public page, reminders, the overview and the CSV.

**The set-up walkthrough and the money course.** `startTour()` (`js/tour.js`) loads `js/tutorials.js` on demand and runs its `setup` tutorial: the first-run tour, and *Take the tour* later. Its cards can carry a form (`body`, saved by `onNext`): the profile cards save name, business, phone, email and website; the calendar card connects Google or Microsoft from the card itself (a sign-in has to start from a tap; `logi-tour-at` resumes the walkthrough after Microsoft's redirect) and names the licence when the device has none; the crew cards add `sample-talent` and `sample-crew` with `upsert` (fixed ids, so a rerun is idempotent) and the last card removes them. `moneycourse` runs on a practice booking (`practice-booking`, flagged `practice: true`, left out of the overdue nudge) whose hooks write the quote and invoice directly with the numbers Q-PRACTICE and INV-PRACTICE, which `nextNumber()` ignores; `openBooking(id, patch)` in `js/pages/bookings.js` is how a hook opens it. `openMoneyGuide()` is the read-through behind **🎓 New to quoting? Start here** on the Money page. Spec 70 walks both.

**The timecode course.** `tccourse` in `js/tutorials.js` is a 27-step walkthrough whose `before` hooks open and close the Sync, Link and Export sheets and switch the notes and script tabs as it goes; cards with `target: null` are read-only interludes. It runs on a practice log that `openPracticeLog()` in `js/pages/tcnotes.js` creates (synced ten minutes ago at 01:00:00:00, three notes, one script mark, the sample script, `practice: true`). `openTcGuide()` is the readable guide, opened from the 📖 button on the logs page, the tutorials chooser and the timecode tutorials' first card. **Cloud sign-in.** `js/cloud-config.js` holds Vdex's own registered app IDs (public by design; see `docs/turn-on-sign-in.md`), so people connect by signing in; a key under Storage, sync & backups → More ways → For developers overrides them on one device. Dropbox and Microsoft use the authorization code flow with PKCE by redirect (`openSignIn`, `dropboxBegin/Finish`, `microsoftBegin/Finish` in `js/providers.js`), with no secret and no library; the return address is the app's folder (`redirectUri(svc)`), and `store.initCloud` finishes the sign-in on return, rolls back a cancelled first connect and leaves the reason in `cloud.notice`. Microsoft's refresh token for a single-page app lasts 24 hours, after which "Sign in again" goes to Microsoft and back with the account as `login_hint`; OneDrive and Outlook share one sign-in. Google uses the Identity Services token model (an hour per token, no silent renewal for a static site): a renewal asks for every scope granted before, so one window covers Drive and Calendar, and names the account so the window can close by itself. In the desktop app sign-ins open in the system browser: `desktop/main.js` accepts the Dropbox/Microsoft redirect only for a `state` the app registered through `signin:open`, and serves a one-time Google page at `/__vdex/google?n=` that posts the token back. iCloud uses Apple's CloudKit web service directly (`icloudAdapter` in `js/providers.js`; no Apple script is loaded): the website gets Apple's sign-in address from a 421 on `users/caller`, goes there and back (the API token's callback is *URL Redirect* to the app folder), and `icloudFinish` takes `ckWebAuthToken` only when `logi-icloud-pending` shows Vdex started that sign-in in the last half hour. The desktop app uses a second token (*Post Message*) on a one-time page at `/__vdex/icloud?n=` in the web browser. The session changes with every answer, so requests run one at a time and keep the newest from the `x-apple-cloudkit-web-auth-token` header; it is saved at once and the lock is told (`vdex-secrets` event) so its sealed copy keeps up, and one that arrives while the lock has cleared the plain copy is held and put back on unlock. The copy is a `VdexFile` record in a zone named `Vdex` in the private database, made on the first save; text over 700 KB is split into part records, written before the main record that names them, and the old parts are removed afterwards. Saves and reads go one at a time, and pushes never overlap or run while locked. *Delete Vdex's copy from iCloud* deletes the zone, so nothing is left behind, after any save under way has finished. Specs 95 (layout and the other services), 96 (iCloud) and the desktop test cover all of this with the services stood in for.

**The desktop app** is `desktop/main.js`: Electron serving these same files from `http://localhost:47831`, so storage and sign-ins behave exactly as in Chrome. It keeps no service worker (`/sw.js` is answered with 404 there, and `js/update.js` removes one a browser left behind): its files come with the installer, and its updates through `desktop/updater.js`. Sign-in pop-ups and the print window stay inside the app; every other link opens in the system browser. Electron has no service-worker notifications, so `js/notify.js` shows plain ones there, and `js/install.js` treats the app as already installed.

**Security notes**
- `index.html` carries a Content Security Policy: scripts only from this origin and the three sign-in / OCR / Microsoft libraries, no inline scripts (the theme pre-paint lives in `js/prepaint.js`), workers from blob URLs for the OCR engine, frames only for Google and Microsoft sign-in, no plugins, no base-URI tricks.
- The two third-party scripts loaded at run time (MSAL and tesseract.js) are pinned to exact versions with Subresource Integrity hashes; Google's sign-in script changes too often for a hash.
- The DOM is built with `h()` text nodes; the only `innerHTML` uses carry generated QR SVG. User links go through `safeUrl` (http or https only); calendar and CSV output is escaped; the call-sheet print window escapes HTML.
- Dropbox sign-in uses PKCE with a random `state` checked on return. Google and Microsoft tokens live in memory or in the libraries' own cache; the Dropbox refresh token and the WebDAV password are kept in localStorage and are part of what the lock encrypts.
- Every device has a PIN: `ensurePin()` (`js/lock.js`) runs after the terms gate and before anything is drawn, and shows the full-screen set-up when `logi-lock` is absent (a first start, or an existing user's next one). The browser specs boot with `logi-lock-setup` = `skip` (`tests/helpers.cjs`, `tests/desktop.mjs`), which skips only that set-up; `gate()` never looks at it, so a PIN that exists always locks (specs 10, 11, 85 and 109).
- A PIN is 4 to 20 digits (`PIN_MIN`, `PIN_MAX`, `pinProblem()` in `js/lock.js`), and nothing within the length is refused. The lock config (`logi-lock`, beside the vault, not in it) records the PIN's length as `len`, so the lock screen draws a dot per digit (two even rows past ten) and sends the PIN by itself at the last one; it takes digits from the keypad, a keyboard and a paste. The config also records `max`, the longest PIN allowed when its PIN was chosen: one without it was made while PINs stopped at 8 digits, and `offerLongerPin()` then fetches `js/pin-offer.js` after the next unlock (ahead of the app at a start, through `ensurePin()`, which waits for the answer but at most five seconds for the file; over the page otherwise). That screen offers **Set a new PIN**, which calls the same `setPin()` re-wrap as Change PIN… and first asks for the current PIN when the unlock was by fingerprint or face, or **Keep my current PIN**; either answer writes `max`, so it shows once per device, and a lock screen coming up over an unanswered offer takes it away until the next unlock. A tab takes the config another tab wrote (`takeConfig()`), so a PIN changed in one is the PIN in all of them; the one kind of write it does not take is a copy from before a change it knows of: a config whose PIN its own has replaced (`setPin()` keeps the salts of the PINs before it in `past`, the last eight), or its own PIN without `max` where it has it. That is what a tab still running a version from before longer PINs writes, the whole config it started with, whenever it counts a wrong try or a lock setting is changed in it; the tab answers by putting its own config back, with the higher of the two counts of wrong tries. A PIN newly set in such a tab has a new salt and is taken like any other. Specs 119 and 120 cover all of it.
- The vault is only ever counted as written when the browser accepted the write: a full store (the plain copy and its encrypted copy share the same 5 MB origin quota) says so once and leaves the plain copy in place rather than sealing, the set-up refuses a PIN whose vault could not be saved, a vault that will not open is put aside (`logi-vault-broken`) and Vdex starts from the plain copy, and a tab only drops the plain copy for a vault it wrote itself (the iv at the head of the stored JSON). Two tabs: a PIN set in one sends a tab still at the terms or the set-up back through the lock gate; an erase in one tab (`vdex-erased`, or the config vanishing from the disk) makes the other let go of its key and start again, so nothing of its copy is written back.
- The app lock (`js/lock.js`, `js/crypto.js`): a random 256-bit data key encrypts the database and those secrets with AES-256-GCM into `logi-vault`; the key is wrapped by a PBKDF2-SHA-256 key derived from the PIN (300,000 iterations, random salt) and, when enrolled, by a WebAuthn platform credential: with the PRF extension the wrapping key comes from the authenticator itself, otherwise the biometric gates a non-extractable key kept in IndexedDB and the assertion signature is verified. Plaintext copies exist only while the app is unlocked and visible; they are removed synchronously on hide, lock and page exit. Wrong PINs are rate-limited and can optionally wipe the device.
- Not covered, by design: the copy in your cloud storage is plain JSON protected by that account; the phone-to-laptop link trusts whoever scanned the code; a short PIN can be brute-forced offline by someone who copies the device's storage, which is why a longer PIN (up to 20 digits; Vdex accepts any within the length and gives no advice) and the device's own lock still matter.

**Platform notes**
- Install prompts come from `beforeinstallprompt` (Chromium); iOS gets written instructions (`js/install.js`).
- The synced-folder storage uses the File System Access API, so it is offered only where `showSaveFilePicker` exists (desktop Chromium).
- Script files, and kit lists as CSV, tab-separated or `.xlsx` files, can be shared into the installed web app through the Web Share Target in `manifest.webmanifest` and `sw.js` (Android Chrome); the Play app's own share filter (`android/`) takes text and Word files only; elsewhere the file picker and paste are used.
- Break notifications are local (service-worker `showNotification` on timers), so they depend on the page staying alive; there is no push server.
- Motion sensors use `DeviceOrientationEvent.requestPermission` where it exists (iOS) and `deviceorientationabsolute` elsewhere.
- The desktop app has no network geolocation (that needs a Google API key in Electron), so the location is entered by hand there.

**The website at crowmade.app.** The home page that lists every app, and the Vdex and Valheim Easy Server pages, are in `crowmade/` (written by `tools/build-crowmade.mjs`) and are published with `tools/deploy-crowmade.sh` to the Cloudflare Pages project `crowmade`. A Pages deployment replaces the whole site, so the script publishes only committed, pushed work and first runs `tools/crowmade-guard.mjs`, which reads the live site and refuses to publish if anything there is missing from `crowmade/`, or has changed since this branch last published it (another session's newer work; `tools/crowmade-published.json` records what went live, so commit and push it after publishing). Little Journee's pages (`/journee/`) are a separate Cloudflare Worker published from the Children-Schedule-App repository, and Vdex itself is at vdex.crowmade.app; neither is touched by this script. The Vdex page's Buy button goes to vdex.crowmade.app/buy, beside the price with tax (the totals come from `js/tax.js`, as on the download page).
