# For developers

Vdex is a static web app: plain HTML, CSS and JavaScript modules, no build step, no framework, no backend.

**Run it locally**
```sh
python3 -m http.server 8000   # then open http://localhost:8000
```
Camera, microphone, location, notifications and installing need https or `localhost`.

**Tests.** `npm install`, then `npx playwright install chromium` once and `npm test`: the browser specs in `tests/specs` run against a scratch copy of the app (the lock and vault, biometric unlock through a virtual authenticator, the call sheet builder and PDF, the update cycle, templates and themes, performance, money, weather and the service log). `npm run test:desktop` launches the desktop app (under `xvfb-run` on Linux). `.github/workflows/tests.yml` runs both on every push and pull request.

**Signing the desktop apps (optional).** Add these repository secrets and the installers come out signed; without them they are unsigned, as before. Mac: `MAC_CERT_P12` (a Developer ID Application certificate exported as .p12 and base64-encoded), `MAC_CERT_PASSWORD`, and for notarization `APPLE_ID`, `APPLE_APP_PASSWORD` (an app-specific password) and `APPLE_TEAM_ID`; a signed and notarized Mac build updates itself through the same release metadata as Windows and Linux, and loses the “unidentified developer” warning. Windows is signed through Azure Artifact Signing: secrets `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` and variables `AZURE_SIGNING_ENDPOINT`, `AZURE_SIGNING_ACCOUNT`, `AZURE_SIGNING_PROFILE`, `AZURE_SIGNING_PUBLISHER` (the owner steps are in `docs/selling-desktop.md`). The Mac build uses the hardened runtime with the entitlements in `desktop/build/entitlements.mac.plist`.

**Where the website comes from.** The app lives at `https://vdex.crowmade.app`: a Cloudflare Worker that serves the static files, plus a small script (`cloudflare/worker.mjs`) that answers only `/buy` and `/licence/…` (owner steps and details in `docs/cloudflare.md` and `docs/selling-desktop.md`). `tools/stage-site.mjs` copies only the website (the pages listed in `tools/site-files.mjs`, `styles.css`, the manifest, `sw.js`, `js/`, `vendor/`, `icons/`, `.well-known/`), never the Android, desktop, docs, store or test sources, and refuses to publish if the offline list or a page names a file it leaves out. The *Publish the website* workflow (`.github/workflows/pages.yml`) works in two steps: a push to the working branch `claude/videographer-gear-app-xlg8eb` runs the browser test suite and, when it passes, the `mirror` job moves `main` to that commit and starts the workflow again on `main`, where the `cloudflare` job stamps the build and publishes it (without testing the same commit twice). So `main` is always exactly what is live, and a broken push never reaches anyone's phone. *Run workflow* on `main` publishes on demand. If the mirror step fails with "not a fast forward", someone committed to `main` directly: merge `main` into the working branch and push again. The old address (GitHub Pages) stopped when the repository went private. Every installed copy picks each update up by itself.

**Releasing updates.** Every push to the working branch deploys the web app once the tests pass (through `main`, as above): the Pages workflow first runs `tools/stamp-build.mjs`, which writes the commit into `js/version.js` and `sw.js` and regenerates the service worker's offline file list from the tree, so every deploy is one versioned set of files and every installed web copy picks it up on its next open (the page checks on start, when it comes to the front, when the network returns and hourly, then offers a reload). For the desktop apps, bump `VERSION` in `js/version.js` and commit, then run **Build desktop installers** with **Publish** ticked (or push a tag such as `v1.3.0`): the workflow builds the installers plus the `latest*.yml` update metadata and uploads them to `https://download.crowmade.app/vdex/` (the `vdex-downloads` R2 bucket; installers first, the `latest*.yml` files last), which installed Windows, Linux and signed Mac apps fetch by themselves through electron-updater (`desktop/updater.js`, generic provider); an unsigned Mac is told and sent to `download.html`.

**Making the installers.** `npm install` once, then `npm run dist -- --win`, `--mac` or `--linux` builds `Vdex-Setup-<version>.exe`, `Vdex-<version>.dmg` (and the `.zip` the Mac updater uses) or `Vdex-<version>.AppImage` into `dist/`, each on its own kind of computer (a Windows build on Linux also needs Wine). `.github/workflows/desktop.yml` builds all three on GitHub: open the **Actions** tab → **Build desktop installers** → **Run workflow**, then download them from the run's Artifacts (kept 3 days), or tick **Publish** to put them on the download address. The version comes from `js/version.js`.

**Desktop licences.** The desktop app has a 30-day trial, then needs a licence code (20 USD, up to 3 computers; free codes from the owner). `desktop/licence-codes.js` is the one implementation of the code format (Ed25519-signed, Crockford base32, Web Crypto only), shared by the desktop app, the Worker and the owner's generator. `desktop/licence.js` keeps the trial clock and the code in `licence.json` in the app's data folder, activates a code online once per computer (`/licence/activate` keeps a list per code in the `LICENCES` KV namespace: a random install ID, Mac/Windows/Linux and two dates) and rechecks weekly; a computer must reach the server once in 90 days. `js/licence.js` shows it in Settings → About and makes the store read-only through `store.setGate` when there is no working licence. The public keys live in `desktop/licence-keys.json`; while it is empty, licensing is off and every install that runs is marked as an early user (free for good). `tools/licence-generator.html` (built by `tools/build-generator.mjs` from its template) is the owner's offline page for keys and free codes, and signs requests to `/licence/admin` to look up, clear, cancel or restore a code. Specs 101–103 cover the format, the desktop rules, the Worker in workerd (needs `npm ci --prefix cloudflare`) and the page.

**The Android app (Google Play)** is `android/`: a Trusted Web Activity generated with Bubblewrap (`@bubblewrap/core` 1.27) from `android/twa-manifest.json`, so the store app is a thin shell that opens the live site in Chrome with no browser UI, and website updates reach it on their own. It targets Android 16 (API 36), asks only for the notifications permission, and registers the web app's share target so files can be shared into it. Its package is `app.crowmade.vdex` (fixed for good by the first Play upload) and its icon opens `https://vdex.crowmade.app/index.html?src=play`. The `src=play` marker only comes with a start from the icon (a link, a share or a reload arrives without it), and nothing reads it yet: the planned website gate will record it on first sight, together with an `android-app://app.crowmade.vdex` referrer. The share target takes real MIME types only (`text/plain`, `text/markdown`, `text/x-markdown` and Word's .docx type): Android refuses to install an app whose share filter lists file extensions, and its action must be the absolute `https://vdex.crowmade.app/share`. `.github/workflows/android.yml` builds the bundle and the apk on every change to `android/` (or by hand), signs them, and keeps them as the run's artifacts for 3 days; the run summary names the signing certificate. The app is no longer published as a public GitHub release, because it is sold on Google Play; the workflow's `unpublish` job removes the old `android-latest` pre-release. The upload key is `android/upload-key.keystore.enc` (AES-256, PBKDF2) and is unlocked with the `ANDROID_KEY_PASSPHRASE` repository secret, which is also the keystore password; without the secret the workflow signs with a throwaway key and says so. `.well-known/assetlinks.json` carries the upload key's certificate fingerprint; Google's own app-signing fingerprint has to be added there after the first Play upload. The file only counts at the root of the site's own domain, `https://vdex.crowmade.app/.well-known/assetlinks.json`. To change the shell (icon, name, start address, version), edit `twa-manifest.json`, raise `appVersionCode`, and regenerate with `npx @bubblewrap/cli@1.27.0 update --manifest=android/twa-manifest.json`, or edit `android/app/build.gradle` directly for the version alone. Store listing texts, the checklist for the account owner and the data safety answers are in `docs/google-play.md`; the store pictures are in `store/android/`.

**Start-up and storage costs.** Only the Bookings section and the shared modules load with the app (28 modules, about 350 KB unminified); the other eight sections and the tutorials are fetched the first time they are opened, and `index.html` lists the start-up modules as `modulepreload` hints so a first visit fetches them in one go instead of discovering the import chain level by level. The service worker registers after the page has loaded and precaches with `cache: 'no-cache'`, so the offline copy costs revalidations rather than a second download. Store writes are coalesced: a burst of changes in one task is serialised and written once, and sealing flushes first. Spec 50 keeps all of this honest: the preload list must equal the real start-up graph, the lazy sections must not load at start-up, and a burst of writes must store once.

**Getting paid** is built around links rather than a processor. `js/pay.js` turns the settings into Pay buttons with the balance and the invoice number filled in (PayPal.Me takes `name/amountCODE`, Venmo and Cash App take the amount in the address, any payment page gets `{amount}` and `{reference}` substituted), plus bank lines and an EPC069-12 payload for the bank QR (euro amounts only, as the standard requires). `snapshot(b, kind)` in `js/money.js` is the self-contained copy of a document that everything renders from; `shareLink` packs it with `js/link-pack.js` into `invoice.html#1.<base64url deflate-raw>` (`0.` when the browser has no CompressionStream), and `js/invoice-page.js` unpacks and draws it with the same `money-doc.js` renderer, so the client's page and the app can never disagree. The fragment never leaves the browser, which is why no server is involved. Payments live on the invoice as `payments[]`; `calc()` derives paid and balance, and an invoice marked Paid with nothing recorded counts as paid in full, which keeps older records right. The ways to pay are a list (`billing.payMethods`, each `{ type, value, label }` or bank fields) drawn from `PAY_TYPES` in `js/pay.js`; `methodsOf()` also reads the older fixed fields, so earlier settings and earlier links still work. Spec 90 covers settings and the catalogue, buttons, QR, payments, the link, the public page, reminders, the overview and the CSV.

**The timecode course.** `tccourse` in `js/tutorials.js` is a 27-step walkthrough whose `before` hooks open and close the Sync, Link and Export sheets and switch the notes and script tabs as it goes; cards with `target: null` are read-only interludes. It runs on a practice log that `openPracticeLog()` in `js/pages/tcnotes.js` creates (synced ten minutes ago at 01:00:00:00, three notes, one script mark, the sample script, `practice: true`). `openTcGuide()` is the readable guide, opened from the 📖 button on the logs page, the tutorials chooser and the timecode tutorials' first card. Spec 70 walks the course and checks the guide.

**Cloud sign-in.** `js/cloud-config.js` holds Vdex's own registered app IDs (public by design; see `docs/turn-on-sign-in.md`), so people connect by signing in; a key under ☁ → More ways → For developers overrides them on one device. Dropbox and Microsoft use the authorization code flow with PKCE by redirect (`openSignIn`, `dropboxBegin/Finish`, `microsoftBegin/Finish` in `js/providers.js`), with no secret and no library; the return address is the app's folder (`redirectUri(svc)`), and `store.initCloud` finishes the sign-in on return, rolls back a cancelled first connect and leaves the reason in `cloud.notice`. Microsoft's refresh token for a single-page app lasts 24 hours, after which "Sign in again" goes to Microsoft and back with the account as `login_hint`; OneDrive and Outlook share one sign-in. Google uses the Identity Services token model (an hour per token, no silent renewal for a static site): a renewal asks for every scope granted before, so one window covers Drive and Calendar, and names the account so the window can close by itself. In the desktop app sign-ins open in the system browser: `desktop/main.js` accepts the Dropbox/Microsoft redirect only for a `state` the app registered through `signin:open`, and serves a one-time Google page at `/__vdex/google?n=` that posts the token back. iCloud uses Apple's CloudKit web service directly (`icloudAdapter` in `js/providers.js`; no Apple script is loaded): the website gets Apple's sign-in address from a 421 on `users/caller`, goes there and back (the API token's callback is *URL Redirect* to the app folder), and `icloudFinish` takes `ckWebAuthToken` only when `logi-icloud-pending` shows Vdex started that sign-in in the last half hour. The desktop app uses a second token (*Post Message*) on a one-time page at `/__vdex/icloud?n=` in the web browser. The session changes with every answer, so requests run one at a time and keep the newest from the `x-apple-cloudkit-web-auth-token` header; it is saved at once and the lock is told (`vdex-secrets` event) so its sealed copy keeps up, and one that arrives while the lock has cleared the plain copy is held and put back on unlock. The copy is a `VdexFile` record in a zone named `Vdex` in the private database, made on the first save; text over 700 KB is split into part records, written before the main record that names them, and the old parts are removed afterwards. Saves and reads go one at a time, and pushes never overlap or run while locked. *Delete Vdex's copy from iCloud* deletes the zone, so nothing is left behind, after any save under way has finished. Specs 95 (layout and the other services), 96 (iCloud) and the desktop test cover all of this with the services stood in for.

**The desktop app** is `desktop/main.js`: Electron serving these same files from `http://localhost:47831`, so the service worker, storage and sign-ins behave exactly as in Chrome. Sign-in pop-ups and the print window stay inside the app; every other link opens in the system browser. Electron has no service-worker notifications, so `js/notify.js` shows plain ones there, and `js/install.js` treats the app as already installed.

**Security notes**
- `index.html` carries a Content Security Policy: scripts only from this origin and the three sign-in / OCR / Microsoft libraries, no inline scripts (the theme pre-paint lives in `js/prepaint.js`), workers from blob URLs for the OCR engine, frames only for Google and Microsoft sign-in, no plugins, no base-URI tricks.
- The two third-party scripts loaded at run time (MSAL and tesseract.js) are pinned to exact versions with Subresource Integrity hashes; Google's sign-in script changes too often for a hash.
- The DOM is built with `h()` text nodes; the only `innerHTML` uses carry generated QR SVG. User links go through `safeUrl` (http or https only); calendar and CSV output is escaped; the call-sheet print window escapes HTML.
- Dropbox sign-in uses PKCE with a random `state` checked on return. Google and Microsoft tokens live in memory or in the libraries' own cache; the Dropbox refresh token and the WebDAV password are kept in localStorage and are part of what the lock encrypts.
- The app lock (`js/lock.js`, `js/crypto.js`): a random 256-bit data key encrypts the database and those secrets with AES-256-GCM into `logi-vault`; the key is wrapped by a PBKDF2-SHA-256 key derived from the PIN (300,000 iterations, random salt) and, when enrolled, by a WebAuthn platform credential: with the PRF extension the wrapping key comes from the authenticator itself, otherwise the biometric gates a non-extractable key kept in IndexedDB and the assertion signature is verified. Plaintext copies exist only while the app is unlocked and visible; they are removed synchronously on hide, lock and page exit. Wrong PINs are rate-limited and can optionally wipe the device.
- Not covered, by design: the copy in your cloud storage is plain JSON protected by that account; the phone-to-laptop link trusts whoever scanned the code; a short PIN can be brute-forced offline by someone who copies the device's storage, which is why 6 or more digits and the device's own lock still matter.

**Platform notes**
- Install prompts come from `beforeinstallprompt` (Chromium); iOS gets written instructions (`js/install.js`).
- The synced-folder storage uses the File System Access API, so it is offered only where `showSaveFilePicker` exists (desktop Chromium).
- Script files can be shared into the app through the Web Share Target in `manifest.webmanifest` and `sw.js` (Android Chrome); elsewhere the file picker and paste are used.
- Break notifications are local (service-worker `showNotification` on timers), so they depend on the page staying alive; there is no push server.
- Motion sensors use `DeviceOrientationEvent.requestPermission` where it exists (iOS) and `deviceorientationabsolute` elsewhere.
- The desktop app has no network geolocation (that needs a Google API key in Electron), so the location is entered by hand there.

**Versions.** The current version is shown under Settings → About. Version 1.0.0 (before the workflow features) is kept on the branch `claude/backup-v1.0.0`.

**The website at crowmade.app.** The home page that lists every app, and the Vdex and Valheim Easy Server pages, are in `crowmade/` (written by `tools/build-crowmade.mjs`) and are published with `tools/deploy-crowmade.sh` to the Cloudflare Pages project `crowmade`.
